# WORKFLOW.md — 前端模块开发分阶段工作流

> **位置**：`docs/agents/WORKFLOW.md`。同目录放三份过程模板（`adr-template.md` / `stage-report.md` / `acceptance-checklist.md`）。
> **本文件回答**：按什么顺序做、每一步问哪 3 句、产出什么、用哪个 skill、怎么验收。
> **本文件不回答**：什么永远不可以 —— 那是 `../AGENTS.md` 硬规则（下文引用 `AGENTS.md` 均指该文件）。
> 两份文档用编号互引、正文不重复。本文件用 `阶段 / D / G / T / L` 系列编号。

---

## 0 · 使用方式

### 0.1 状态机

```
阶段 0 侦察 ──→ 阶段 1 需求确认 ──→ 阶段 2 方案评审 ──→ 阶段 3 实现 ──→ 阶段 4 自检 ──→ 阶段 5 验收交付
   只读            逐条闭合            方案 + 决策点        按 T 逐项        四闸门          截图 + 交付说明
                    │                    │                   │              │                │
                 R1 载体              R3 载体             R4 载体        R6 载体          用户确认
              （无待确认条目）    （方案存在 + D 全裁定）（差异有答复）（四闸门全绿）
```

**阶段不可跳跃、不可并行。** 每阶段结束时输出阶段报告（`AGENTS.md` 硬规则 `R5`，格式见 `F2`），报告在进入下一阶段前给出，让用户有机会叫停。

### 0.2 三条贯穿全程的规矩

1. **每次向用户确认某个细节 = 一次 `AskUserQuestion` 调用 = 恰好 3 个 question**（`AGENTS.md` 硬规则 `R2`）。提问前先给「我的理解 / 我看到的依据 / 我担心什么」三句前言。
2. **skill 是参考，不是决策来源**（`AGENTS.md` 硬规则 `S1`）。skill 与项目现状冲突 → 进决策点由用户裁定。**只用已安装且登记在 §5.1 清单内的 skill**；清单之外的 skill 一律不引用。
3. **一切读写只在项目根目录内**（`AGENTS.md` 硬规则 `R7`）。需要范围外信息时向用户索取，不自行读取。

## 2 · 阶段详解

### 阶段 0 · 侦察 Recon

**目标**：把"项目现状"变成**在本项目内实测过的一手基线**，并锁定本次模块的归属与形态。

**进入条件**：用户已把完整前端项目拷入项目根目录；`AGENTS.md` 硬规则 与 `WORKFLOW.md` 已就位。

> ⚠️ **范围硬约束（`AGENTS.md` 硬规则 `R7`）**：本阶段**只读**，且**只在项目根目录内**读。
> 不读其它项目、不读用户主目录、不读全局配置、不读包管理器缓存内容。
> 需要范围外信息时，向用户索取，不自行获取。

**必须做的动作**（逐条打勾，缺一不得退出）：

0. **判定工作根**：项目根目录内是否存在唯一 `package.json`？
   - 唯一 ⇒ 代码根 = 其所在目录；
   - 无（空目录 / 纯新建）⇒ 代码根 = 项目根目录；
   - 多个候选 ⇒ 记入「缺失项」，并进入 3 问由用户指定。

   **此判定不预设**；阶段 0 的所有后续侦察都以判定出的代码根为界。
1. **依赖与脚本**：读 `package.json`，记录框架 / 语言 / 构建工具 / 测试工具的**实际版本**，以及 `scripts` 的全部条目。
   **重点确认**：`lint` 类脚本是否带会自动改写文件的参数（`--fix` / `--write`）？`build` 是否已内含类型检查？有无 `test` 脚本？有无任何测试相关依赖？
2. **构建与工具配置**：读构建配置、`tsconfig*`、ESLint 配置、Prettier 配置、路径别名。记录**已关闭的规则**（例如类型严格度相关）。
3. **源码结构**：枚举 `src/` 全部一级目录，产出一份目录清单，标注每个目录的职责。
4. **公共层**（改动风险最高，逐个读）：
   - 请求封装：拦截器做了什么？响应是否统一信封？错误如何提示？鉴权失效如何处理？
   - 类型契约：共享类型定义在哪？分页结构长什么样？错误码怎么组织？
   - 路由注册：是静态配置还是由后端/配置驱动？路由元信息带什么？
   - 全局 store：有哪些？state 形状？哪些字段被持久化？
   - 共享校验规则：有没有规则工厂？类型是什么？
   - 权限：有没有权限工具函数或指令？权限码形态？
5. **领域资源**：枚举 API 层模块清单与领域字典 / 常量清单，标出与本次模块相关的 1–3 项。
6. **最近似既有视图**：选 **1 个**与本次模块形态最接近的既有视图通读，把它的文件头注释约定、页面骨架结构、搜索区写法、表格写法、弹窗写法、命名风格逐条抄录成"本项目模板"。**这是后续所有代码风格的事实来源**（`R3` 载体之一）。
7. **测试基建**：确认测试工具链是否存在、能否运行、现有测试的组织方式与命名约定。**零基建要如实记录**。
8. **文案现状**：统计现有视图里硬编码文案与国际化 key 的比例，作为 D10 的依据。
9. **基线偏差表**：把上面每条结论落成一张表（结论 / 证据文件路径 / 是否与预期一致），进 `baseline.md`。**每条结论必须有文件路径作为证据**，不许凭印象。
10. **git 状态**：若项目根目录**不是** git 仓库 —— **不要自行 `git init`**。这属于对项目环境的改动，如需要，向用户提出（一次 3 问）。

**本阶段 3 问模板**（必须在完成 1–9 的实测**之后**发问，正文引用你刚读到的具体文件）：

```
**我对当前情况的理解**：<一句话说清项目实际技术栈与结构，引用具体文件路径>
**我看到的依据**：<3–5 条关键发现，每条带文件路径>
**我担心的是**：模块归属或形态定错，会导致后续的字典来源、权限码、菜单配置全部返工。

Q1（模块归属）本次要开发的模块归属哪个业务域？
  - A. 在既有业务域内扩展（列出侦察到的可选业务域）
  - B. 新增业务域（需要同时设计菜单 / 权限码 / 领域字典三项）
  - C. 跨 ≥2 个业务域的组合功能
  - D. 还没定 —— 请先列出 3 个候选模块及各自涉及的资源，我再选

Q2（模块形态）模块的主体形态是哪一种？
  - A. 列表 CRUD（搜索区 + 表格 + 分页 + 弹窗表单）
  - B. 列表 + 独立详情 / 编辑页（需要登记路由）
  - C. 看板 / 分析（以图表为主）
  - D. 录入 / 审批流（表单为主且有状态流转）
  - E. 其它 —— 请描述

Q3（接口就绪度）后端接口目前处于什么状态？
  - A. 接口已上线且稳定，可直接联调
  - B. 路径与字段已定，但分页方式 / 错误码 / 字典接口未最终确认
  - C. 接口未开发 —— 本次需先产出接口契约草案
  - D. 现阶段无后端 —— 先用本地 mock 跑通前端
```

**退出条件**：`baseline.md` 已生成且偏差表逐条有结论与证据路径；`module-scope.md` 已生成；上面 3 问已获答复且 Q1、Q2 各自有唯一答案。

**skill 与文档产出**：框架最佳实践类 skill（**只读** —— 用于标注项目实际写法与官方推荐的差异，供阶段 2 引用，不得据此改代码）。
`baseline.md` 与 `module-scope.md` 为**内置文档动作**：直接撰写（偏差表 + 模块归属结论），不依赖任何 skill。

### 阶段 1 · 需求确认 Requirements

**目标**：把用户的模糊描述拆成**逐条可确认**的条目，让每条都落到「已确认 / 用户豁免」，实现 `AGENTS.md` 硬规则 `R1` 的载体。

**进入条件**：阶段 0 通过；模块归属与形态唯一确定。

**必须做的动作**：

1. 把用户原始需求拆成条目，类型至少覆盖：功能点、字段与来源、校验规则、交互与边界、错误处理、权限、字典与常量、文案、视觉、性能与数据量、验收方式。
2. 每条标注：① **候选解释 ≥2 种**；② **不确认会返工在哪**；③ **属重决策还是轻决策**。
3. 重决策条目在本阶段**只登记不裁定**（裁定在阶段 2），但必须先确认它的**前提事实**。
4. 每轮 3 问（见下），答复后**立刻回写** `requirements.md`（问编号 → 用户选项原文 → 落到条目号）。
5. 维护「**不做清单**」，防止范围蔓延。
6. 滚动多轮直到条目全部闭合。**每轮结束做一次小结**：本轮确认了什么、还剩几个待确认。

**本阶段 3 问模板**（通用骨架，每轮固定这个配比）：

- **Q1 事实/边界**：这条需求的确切事实是什么？（通常带 2–4 个互斥事实选项）
- **Q2 取舍/优先级**：当两者不能兼得时优先哪个？
- **Q3 验收/细节**：做到什么程度算完成？

**变体 A · 列表 CRUD 型模块**：

```
Q1（字段与来源）列表页要展示的列，数据来源是？
  - A. 列表接口直接返回展示值（含文案）
  - B. 列表接口返回编码值，展示层用项目既有领域字典翻译
  - C. 列表接口返回编码值，另有字典接口，前端缓存
  - D. 部分列需额外调详情接口补全 —— 请指出是哪几列

Q2（校验与字典落位）表单校验规则与字典常量放在哪里？
  - A. 新增到项目既有的共享规则 / 字典文件，沿用既有风格
  - B. 字典进共享目录，校验规则留在模块内
  - C. 两者都放模块内，不进共享目录
  - D. 先把既有共享文件里可复用的列出来，我确认后再定

Q3（交互边界）列表区关键交互按哪种处理？
  - A. 全部沿用既有同类页面的做法（我会先给你看最接近的一页做对照）
  - B. 沿用做法，但列宽 / 密度 / 分页位置允许我调整
  - C. 需要新交互形态（批量选择 / 树形表格 / 拖拽排序 / 行内编辑）
  - D. 这些细节等阶段 2 的方案一起看
```

**变体 B · 看板 / 分析型模块**：

```
Q1（指标口径）核心指标、口径与时间粒度是？
  - A. 指标与口径由后端固化，前端只做展示
  - B. 口径由前端计算（需要约定时间范围与分桶规则）
  - C. 多个指标各自独立接口，前端并发请求后拼装
  - D. 需要支持自定义时间范围筛选

Q2（空态与权限）无数据 / 加载中 / 无权限三种状态分别怎么表现？
  - A. 沿用项目既有的空态与加载样式
  - B. 无权限时隐藏模块入口（前端隐藏 + 路由守卫双保险）
  - C. 无权限时保留入口但显示占位提示
  - D. 按可访问性建议给出一版，由你选

Q3（刷新与性能）数据刷新策略是？
  - A. 进页面拉一次 + 手动刷新按钮
  - B. 定时轮询 —— 请指定间隔
  - C. 依赖既有 store 缓存，切页不重复请求
  - D. 数据量大，需要分页 / 虚拟滚动 / 预取
```

**退出条件**：`requirements.md` 中**无任何「待确认」条目**；每条为「已确认（含用户选项原文）」或「用户豁免（含豁免理由）」；不做清单已明确（可为空，但必须写明"经确认不做：X"）。

**skill**：设计规范类 skill（**只读** —— 交互与可访问性硬性约束清单）、框架最佳实践类 skill（**只读** —— 避免提出的方案违背框架约束）。

### 阶段 2 · 方案评审 Design Review（重点阶段）

**目标**：产出**文件级方案**与**编号决策点 D1..Dn**，把技术未知项**逐条由用户裁定**，并落 ADR 留痕。这是 `R3` 的载体。

**进入条件**：阶段 1 闭合（无待确认条目）。

**必须做的动作**：

1. **写方案** `plan.md`，分层（数据层 → 状态层 → 组件层 → 视图层 → 样式层 → 测试层），逐文件标注 **新增 / 修改 / 不改动**，并列出 **T1..Tn** 任务分解（每个 T = 一个关注点、一次可回退的改动）。
2. 把技术未知项映射为 **D1..Dn**（见 §4）。
3. 每个 D 点按**三件套起步**展开（决策点若还有额外维度，继续编号 S4、S5…）：
   - **S1 核心取舍**：这个决策点有哪几个**互斥**方案？（2–4 个）
   - **S2 成本与副作用**：每个方案要新增几个依赖 / 改动几个公共文件 / 影响几个存量模块 / 是否需要后端配合？你能接受到哪一档？
   - **S3 验收与可逆**：这条决策「做到什么算完」？选错了怎么回退？要什么测试或截图来证明？
4. 按 §3 轮次编排，把所有 S 排进「每轮恰好 3 问」的 `AskUserQuestion`。
5. 每个 D 点裁定后**立刻写 ADR**：`decisions/ADR-000X-<slug>.md`，**按 `adr-template.md` 模板填写**（模板源在本文件同目录 `docs/agents/`，实跑时复制到项目 `.workflow/templates/`），含 Context / Options / Decision / Consequences / 关联需求条目号 / 关联文件路径。（内置文档动作，不依赖 skill）
6. 明确写「**本次不做清单**」与「**后续可能需要回头评估的点**」。
7. **收口三问**做方案整体确认（见下）。

**每个 D 点的提问格式（示例，D1 完整展开）**：

```
### D1 数据层方案

**D1-S1（核心取舍）数据层走哪条路？**
  - A. 维持现状：只用项目既有的请求封装 + 统一响应信封 + 全局错误提示
  - B. 引入 TanStack Query for Vue，但把它包成一层适配器：queryFn 复用既有封装，并关掉全局提示避免双弹
```

## 3 · 轮次编排协议

```
1. 收集所有待问子问题（每个决策点 3 个：S1 / S2 / S3；每个阶段 1 组 3 问）。
2. 排序：
   - 同一决策点的 S1 必须先于它的 S2 / S3 —— 没有 S1 的裁定，S2 / S3 无从比较。
   - 高影响的 S1 优先（数据层 → 校验 → 路由 → 测试）。
3. 每轮取 3 个问题，装进一次 AskUserQuestion（3 个 question，每问 2–4 个 options）。
4. 轮内 3 问尽量来自不同决策点，避免同一决策点的 S1/S2/S3 同轮出现导致选项互相干扰；
   若某决策点只剩 S2/S3，允许同轮出现，但正文须标注"承接上一轮裁定"。
5. 每轮结束输出本轮小结（确认了什么 / 剩余问题数），并回写留痕。
6. 用户选"都不对"时，按 AGENTS.md 硬规则 Q5 重构 3 个新问题，不重复原问题。
```

## 6 · 验收闸门（阶段 4）

> 本章是 `AGENTS.md` 硬规则 `R6`（四项闸门 + 失败必须阻塞）的执行细则；具体命令与处置分级如下。
> **端别映射**：本节命令是前端（Vue 3 + Vite + TS）形态；后端任务的四闸门按 `docs/backend/08 §4` 执行（单测全绿 / 零依赖校验 / curl 实跑冒烟 / 安全自检），处置分级表词表替换见其 §5。

### 6.1 命令序列

> ⚠️ **闸门命令一律由阶段 0 抄录的 `scripts` 原文推导，不得凭印象写命令。**
> 下列命令名是**通用形态**（Vue 3 + Vite + TS 基线栈），需按项目实际情况替换。
>
> **命令生成规则**：
> 1. 优先用项目里实际存在的脚本；不存在对应脚本时，才考虑 `npx <tool>` 通用形式。
> 2. 带 `--fix` / `--write` 的脚本**只能当收尾格式化**，不能当闸门。闸门用其**剥离自动改写参数后的等价只读命令**。
> 3. 剥离后命令若失去意义（如脚本本身就是 `prettier --write`），**不做剥离**，改为记录"该脚本不可用作闸门"，并按需触发 D7 拍板是否新增只读脚本。
> 4. 类型检查若项目无独立脚本：用构建脚本中的类型检查步骤；若两者皆无 ⇒ 属重决策，走 D 清单问用户是否新增脚本，**不擅自加**。

```bash
# ── G0 变更范围核查（证明只改了允许范围，对应 R3 / W1–W4）
#   代码根若是版本控制仓库：git -C <代码根> status --porcelain && git -C <代码根> diff --stat
#   否则：记录本次新建 / 修改的文件清单，与方案中的「新增/修改」列表逐项比对
#   ⚠️ 若代码根不是 git 仓库，不要自行 git init —— 按 AGENTS.md 硬规则 A3 先问用户

# ── G1 类型检查（快、报错最干净）
npx vue-tsc --noEmit
#   若项目 build 脚本已内含类型检查，G1 可与 G4 合并

# ── G2 只读 Lint 闸门 —— 绝对不带 --fix / --write
npx eslint . --ext .vue,.js,.ts --max-warnings 0
#   若 D7 裁定新增了只读 lint 脚本，则改用该脚本（同样不得带 --fix）

# ── G3 单元测试（仅当 D7 批准引入测试栈后存在）
npx vitest run --reporter=verbose

# ── G4 生产构建（G1 的延伸校验，不单列为独立闸门；build 已含类型检查时与 G1 合并）
npm run build

# ── G5 浏览器实跑 + 截图（阶段 5，内置动作）
npm run dev   →  驱动浏览器逐条走查  →  screenshots/
```

### 6.2 为什么这样排

| 关注点 | 处理 |
|---|---|
| **lint 脚本可能带 `--fix`** | 它会**自动改源码、掩盖问题、使闸门永远绿**。闸门**只用不带 `--fix` 的只读命令**（`X2`）。项目自带的 `lint` 脚本只能当收尾格式化单独执行，且执行前后必须用 `git diff` 公示改动。 |
| **build 脚本可能已含类型检查** | 因此 G1 单独跑类型检查（快、报错可读），G4 用 `build` 校验产物；G1 已红时不必浪费时间跑 G4。 |
| **零测试基建** | G3 在 D7 裁定前**不存在**。若 D7 选择"不引入"，阶段 4 必须产出一条**显式缺口声明**并走 `F3` 阻塞，直到用户**书面豁免**该验收项，才允许进入阶段 5。 |
| **实跑前置** | 实跑可能需要登录态、可用账号、后端服务。缺失时走 `F3` 问用户，不自行编造账号或改后端。 |
| **`--max-warnings 0`** | 阈值由 D7 裁定；未裁定前按最严执行，但存量 warning 记为"存量"，不阻塞。 |

### 6.3 失败处置分级表

| 失败类型 | 判定依据 | 处置 | 阻塞交付 |
|---|---|---|---|
| 类型错误，修复会动到**公共层 / 数据契约** | 需改 `W2` 文件 | **走 `F3` 阻塞报告**，列方案与代价 | **阻塞** |
| 类型错误，修复是**局部收窄 / 标注** | 只改本次新增文件 | 自主修（轻决策），进 `F1` 公示 | 不阻塞 |
| 类型错误，位于**未改动的存量文件** | `git diff` 未触碰 | 登记进基线偏差表，交付说明列出，**不修** | 不阻塞（须声明） |
| Lint **error**，位于改动文件 | — | 自主修（命名 / 顺序 / 格式），进 `F1` 公示 | 不阻塞 |
| Lint **error**，位于未改动文件 | — | 登记，**不跑 `--fix` 掩盖** | 不阻塞（须声明） |
| Lint **warning** | — | 按 D7 阈值判定；未裁定前记录数量 | 视 D7 |
| 单测失败，根因是**实现 bug** | 断言与实现不符 | 修复后重跑；若修复会改变**产品语义** ⇒ 停 + 3 问 | **阻塞**直到修复或用户裁定 |
| 单测失败，根因是**断言期望本身不确定** | 需求未定义 | 停 + 3 问确认期望行为 | **阻塞** |
| 无测试基建且 D7 拒绝引入 | — | 显式声明"无单测"缺口 | **阻塞**，直到用户书面豁免 |
| `build` 失败 | — | 按上表类型错误分类处理 | **阻塞** |
| 浏览器白屏 / 控制台未处理报错，根因在**公共层** | — | 用运行期排障类 skill 定位后走 `F3` | **阻塞** |
| 浏览器白屏，根因在本次新增代码 | — | 自主修（轻决策）并公示；修后**必须重跑 G1–G4** | 不阻塞 |
| 实跑行为与 `requirements.md` 不符 | — | 停 + 3 问，按用户答复修；不自行"修到看起来对" | **阻塞** |
| 需要为通过而加 `any` / `as any` / `@ts-ignore` / 删断言 | — | **禁止**（`X1` / `X3`），走 `F3` | **阻塞** |

### 6.4 闸门禁止事项

1. 禁止用会自动改写文件的 lint 命令之后再宣称"lint 通过"（`X2`）。
2. 禁止为了让类型检查变绿而给代码加 `any` / `as any` / `@ts-ignore`（`X1`）。
3. 禁止为了让测试变绿而删断言、改快照、放宽期望（`X3`）。
4. 禁止在未获用户批准时修改 `package.json` 的依赖或 scripts（`X4`）。
5. 禁止跳过 G5 浏览器实跑与截图直接交付（`X5`）。
6. 禁止把存量遗留失败静默修掉并混入本次改动（`X6`）。
7. 禁止在阶段 1 / 阶段 2 的载体未满足时做任何业务改动（`X7`）。

## 8 · 例外与降级

| 情形 | 处理 |
|---|---|
| 用户显式豁免某项验收标准 | 记入 `requirements.md` 与 `delivery.md` 的「已知缺口」，**必须写明豁免人、豁免项、影响**，不得静默跳过 |
| 用户要求跳过阶段 | 按 `AGENTS.md` 硬规则 `X-2` 记录这条例外到阶段报告 |
| 项目缺少某类能力（如零测试基建） | 走 `F3` 阻塞，由用户选择「引入依赖」或「豁免验收项」 |
| 发现范围外信息需求 | 按 `R7.3` 向用户索取，不得自行读取 |
| 阶段卡住超过一轮 | 用 `F3` 明确写出「在你答复前我不会做什么」，避免沉默等待 |
| 流程需要 skill 清单之外的能力 | 按内置动作直接执行（见 §5 前言）；若确需引入新 skill，走 `AGENTS.md` 硬规则 `S4` 重决策 |
