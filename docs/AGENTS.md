# AGENTS.md — 前端模块开发硬规则

> **本文件回答**：什么永远不可以、什么时候必须停下来问、该问几个问题、怎么报告。
> **本文件不回答**：先做哪一步 —— 那是 `agents/WORKFLOW.md`。
>
> 本文件与 `agents/WORKFLOW.md` 用编号互引、**正文不重复**：
> 本文件用 `R / Q / A / W / F / X / S` 系列编号；`agents/WORKFLOW.md` 用 `阶段 / D / G / T / L` 系列编号。
> 引用对方时**只写编号**，不复制整句。

## 0 · 适用范围与优先级

| 项 | 内容 |
| --- | --- |
| 工作区 | 本仓库根目录及其全部子目录。除此之外无工作区。 |
| 任务性质 | 为**本仓库的前端或后端**编写**某一个模块**。端别由任务指明；不明确时按 `R2` 三问确认。 |
| 技术栈锁定 | 前端：Vue 3 + TypeScript + Vite，以 `docs/frontend/` 为准。后端：Node.js ≥ 22 + ESM `.mjs` + 零 npm 运行时依赖，以 `docs/backend/` 为准。状态管理 / 数据层 / 表单方案 / 测试工具链等**技术未知项**由 `agents/WORKFLOW.md` 阶段 0 侦察得出、阶段 2 由用户拍板。 |

**优先级（高 → 低）**

1. 用户在当前对话中的显式指令
2. 本文件（硬规则）
3. `agents/WORKFLOW.md`
4. 任何 skill 的内置最佳实践

**冲突仲裁**：skill 建议与本文件或项目现状冲突时，**以本文件与项目现状为准**。想采纳 skill 的做法，必须先把它写成 `agents/WORKFLOW.md` 阶段 2 的一个决策点（`D*`），经用户裁定后才可执行。
**skill 永远不能成为"不提问就动手"的依据。**（见 `S1` / `S2`）

**本文件不授予任何权限。** 它只做两件事：**限制**（哪些事不许做）与**要求**（哪些事必须先问）。
文中出现的任何"允许 / 可以 / 可自主"表述，均指**在不违反上层权限与范围约束的前提下**，**不构成对上层权限的放宽**。
本文件**不能**授权访问范围外路径、跳过闸门、静默修改失败、替代用户做决策，或执行任何破坏性与对外可见的操作。

## 1 · 不可绕过的执行协议

### 每条规则都配一个「载体」

> **载体 = 该规则是否被满足的客观判据**。载体不满足，就不能进入下一阶段。
> 这让规则从"建议"变成**流程闸门**。

### R1 · 每个问题、每个细节都要确认，不替用户决策

- **内容**：任何会影响产出结果的问题、细节、偏好、取舍，都要主动向用户确认，不得凭猜测默认值推进。
- **载体**：阶段 1 的需求清单中**不存在「待确认」条目** —— 每条必须是「已确认（附用户选项原文）」或「用户豁免（附豁免理由）」。只要还有一条待确认，**阶段 1 不得退出，阶段 2 不得开始**。

### R2 · 每次确认某个细节，必须提出三个问题

- **内容**：每轮确认**固定 3 个问题**。少于 3 个是违规，多于 3 个必须拆轮。
- **载体**：每次提问使用**一次** `AskUserQuestion` 调用，其中**恰好 3 个 question**，每个 question 的 options 数量在 **2–4** 之间。
  - options < 2 ⇒ 等于变相替用户决策，违规；
  - options > 4 ⇒ 用户无法有效比较，无效提问，必须重问。
- **细则**：
  - 3 个 question 必须**互相独立**，不得是同一件事的三种说法。
  - 推荐配比：**Q1 事实/边界** · **Q2 取舍/优先级** · **Q3 验收/细节**。
  - **提问前必须先在正文给出三句前言**：① 我对当前情况的理解（引用具体文件路径）② 我看到的代码依据 ③ 我担心的是什么。禁止夹带"我打算怎么做"的既成事实。
  - 提问必须给出 2–4 个**互斥方案**，不能给开放式空白。

### R3 · 未确定需求与方向前不允许盲目执行；先制定方案，再逐一按规划执行

- **内容**：方案获认可前**不得编写业务代码**（组件、页面、API 层、类型、样式均算）。获认可后按阶段逐一执行，不跳阶段、不并行推进未确认阶段。
- **载体**：`agents/WORKFLOW.md` 阶段 2 的方案文件存在、且 `D1..Dn` **全部裁定完毕**之前，**禁止对业务代码路径执行任何 Write/Edit**。只允许只读侦察与提问。
- **细则**：
  - 方案必须落到**文件级**：逐条写明「新增 / 修改 / 不改动」三类路径。
  - 实现阶段只允许改方案中标记为「新增」「修改」的文件；改到其它文件 ⇒ 立即触发 `R4`。
  - "计划外的正确实现"**不构成**跳过 `R4` 的理由。
  - 方案需**实质变更**（增删功能、改架构、扩大范围）时，必须回到阶段 2 重新取得认可。

### R4 · 出现问题或需要决策的部分，主动询问用户，由用户决策

- **内容**：决策点默认**停下来问**，不得"先按最合理的方案做、事后再说"。不得自行决定并执行。
- **载体**：阶段 3/4 每一次遇到方案未覆盖的差异，都必须有一条**对应的用户答复记录**；无答复记录即视为该差异未处理。
- **细则**：用户裁决后，把该决策**写进 ADR**（`.workflow/outputs/<task-id>/decisions/`），记录裁决、理由、影响范围，避免后续丢失。

### R5 · 阶段报告义务

- **内容**：每阶段结束必须输出一份阶段报告。
- **载体**：阶段报告文件存在，且含**轻决策公示表**（`F1`）；轻决策**一条不能少、不得合并概括**。
- **细则**：报告必须在**进入下一阶段之前**输出，让用户有机会叫停。

### R6 · 验收与失败处理

- **内容**：验收闸门固定为四项：**类型检查、Lint、单元测试、浏览器实跑 + 截图**。四项全通过才算完成。
  - **端别映射**：前端任务按 `docs/frontend/00 §4` 执行上表；后端任务按 `docs/backend/08 §4` 执行映射后的四闸门（单测全绿 / 零依赖校验 / curl 实跑冒烟 / 安全自检）——无 TS 无构建，类型检查与浏览器实跑由等价闸门覆盖。
  - 生产构建校验（`build`）**归属类型检查闸门的延伸**，不单列为第五项；若项目 `build` 脚本已内含类型检查，二者合并执行。
  - 若项目缺失某一项的基建（如无测试栈），该项按 `D7` 裁定：要么引入，要么由用户**书面豁免**，不得默认跳过。
- **载体**：阶段 4 自检记录中四项闸门**全部为绿**，且截图文件存在且可读。
- **细则**：自检失败必须**如实报告并阻塞交付**，不得静默修复后当作通过（见 `X`）。

### R7 · 工作范围约束（优先级最高）

| 编号 | 规则 |
| --- | --- |
| **R7.1** | 所有文件**读取、写入、搜索、修改**必须限制在**项目根目录之内**。 |
| **R7.2** | **禁止访问项目根目录之外的任何路径** —— 包括其它项目目录、用户主目录、全局配置目录、npm 全局缓存、其它仓库。**侦察阶段（阶段 0）同样受此约束。** |
| **R7.3** | 需要范围外信息时（例如"另一个项目里有类似实现"、"某个全局配置长什么样"），**只能向用户索取**，不得自行读取。 |
| **R7.4** | **禁止删除或修改范围外的任何既有文件**，包括全局安装的 skill、用户配置、其它项目内容。 |
| **R7.5** | 执行会写入范围外的命令（`npm install -g`、写入用户配置目录的命令、卸载全局包）前，**必须先向用户说明并取得同意**。 |
| **R7.6** | 引用外部知识（skill 内容、公开文档）可以，但**落地产物**必须写在项目根目录内。 |
| **R7.7** | 载体：本次会话中所有工具调用的路径参数，都落在项目根目录内。 |
| **R7.8** | **工具副作用豁免**：包管理器下载依赖必然写入自己的全局缓存、启动开发服务器必然占用本地端口、lint/format 工具必然写临时文件 —— 这类**工具自身的缓存与端口行为不视为越界**。但：**不得主动读取缓存内容当作项目文件**、**不得把缓存产物复制进项目**、**不得在项目根目录之外主动创建目录或文件**。 |

## 2 · 提问协议

| 编号 | 规定 |
| --- | --- |
| **Q1** | 所有面向用户的问题一律用 `AskUserQuestion` 呈现，不用纯文本罗列式提问。 |
| **Q2** | 一轮**恰好 3 个 question**，每问 **2–4 个 options**。 |
| **Q3** | 每轮提问前先给出「我的理解 / 我看到的代码依据 / 我担心什么」三句前言（`R2` 细则）。 |
| **Q4** | 每轮提问后必须把用户答复**回写**到需求清单或 ADR，形成留痕。 |
| **Q5** | 用户答复「其他 / 都不对」时，**不重复原问题**，而是基于新信息重构 3 个新问题继续。 |
| **Q6** | 用户答复「随便 / 你看着办 / 都行」时，**必须再追问一轮 3 问**把选择收敛，**不得**自行填补。 |
| **Q7** | 阶段 4 的闸门失败、阶段 5 的实跑偏差，**同样适用本协议**，不得以"技术问题"为由自行判定。 |

### 标准提问模板

```markdown
**我对当前情况的理解**：<一句话说清现状，引用具体文件路径>
**我看到的依据**：<具体文件/代码/命令输出>
**我担心的是**：<若不确认会导致什么后果>

Q1（事实/边界）：<一个只能由用户回答的事实性问题>
  - 选项 A / B / C
Q2（取舍/优先级）：<一个需要用户排优先级的问题>
  - 选项 A / B / C
Q3（验收/细节）：<一个决定"做到什么算完"的问题>
  - 选项 A / B / C
```

## 3 · 决策自主权分级

### A1 · 判定表

| 等级 | 判定 | 处理方式 |
| --- | --- | --- |
| **重决策** | 架构结构 / 数据契约 / 接口字段与路径 / 响应结构与错误码语义 / 分页语义 / 状态形状与归属 / 路由注册方式与路径设计 / 权限模型 / 表单方案与校验体系 / UI 视觉基调 / 组件库选择 / 依赖引入与移除 / 目录结构重整 / 国际化策略 / 测试框架选型 / 验收标准调整；**后端等价项**：响应信封与错误码分段 / `<pool>/<model>` 路由语义 / 新增池或上游端点 / 调度权重公式与冷却熔断语义 / `data/` 落盘结构 / 引入 npm 运行时依赖 / 新增面板端点 | **停下来问用户**（`R2` 三问），拿到裁定后才动 |
| **轻决策** | 命名（变量 / 函数 / 组件 / 文件）/ 文件组织与位置（项目既有约定内）/ 注释措辞 / 格式化与 import 顺序 / 展示细节（列宽、间距、字号）/ 抽取常量的位置 / 已被认可方案内的具体实现方式选择 | **自主决定**，并在阶段报告中按 `F1` 公示，用户可推翻 |
| **灰区** | 任何"改了会影响别的文件 / 改变运行时可观察行为 / 引入新概念或新依赖"的改动 | **一律按重决策处理** |

### A2 · 三问判定法（灰区裁决，依次问自己，命中任一即为重决策）

1. 这个改动**会被项目内其它文件或后端依赖**吗？（改共享请求封装、改类型契约、改路由注册约定 ⇒ 是）
2. 这个改动**会改变运行时可观察行为**吗？（请求形状、路由表、状态持久化 key、全局错误提示 ⇒ 是）
3. 这个改动**引入了一个新概念或新依赖**吗？（新库、新数据流模式、新目录体系 ⇒ 是）

### A3 · 必须停下来问的场景（命中即停）

- 需要新增、删除或升级任何 npm 依赖（运行时或开发时）
- 需要改动**公共层**：请求封装 / 类型契约 / 路由注册 / 全局 store / 共享校验规则 / 权限工具；后端对应 `W2` 所列公共层（信封、调度、鉴权、adapter）
- 需要改动 `package.json` 的 `scripts`（例如新增一个只读 lint 闸门脚本）
- 需要改变 UI 视觉基调（主题变量、配色、字体、组件库换肤）
- 需要改变国际化策略（是否全量入 locale 文件）
- 需要引入测试框架或改变测试策略
- 需要改动方案中未标记为「新增/修改」的文件
- 实现中发现方案未覆盖的差异
- 闸门失败且根因落在公共层
- **任何"我不确定用户想要哪个"的地方**（不确定就是问，不是猜）

### A4 · 轻决策的公示义务

每一处轻决策必须进入阶段报告的 `F1` 公示块，且**必须可被用户一眼推翻**（给出文件路径与影响范围）。

### A5 · 禁止用"工程判断"替代提问

下列说法**不构成**跳过提问的理由：
"这是最佳实践" / "skill 建议如此" / "业界都这么做" / "应该没问题" / "先做了再看" / "先按常规来"。

## 4 · 文件可写边界

| 类别 | 路径 | 说明 |
| --- | --- | --- |
| **W1 · 可直接写** | 本文件、`agents/WORKFLOW.md`、`.workflow/**`、以及方案中标记为「新增/修改」的文件 | 写完按 `F1` 公示 |

## 5 · 报告与公示格式

### F1 · 轻决策公示块（每阶段报告**必须原样包含**，一条不能少）

```markdown
## 本阶段自主决策（轻决策）公示

| # | 决策内容 | 我的选择 | 理由 | 影响文件 | 可推翻 |
|---|---------|---------|------|---------|--------|
| L1 | 例：搜索区字段顺序 | 先按查询频次排序 | 与项目既有同类页面一致 | src/.../index.vue | 是 |
| L2 | 例：空列表文案 | "暂无数据" | 复用项目既有措辞 | src/.../index.vue | 是 |
```

### F2 · 阶段报告必备字段

1. 本阶段目标与实际完成情况
2. 执行过的命令与关键结果（成功 / 失败各一行）
3. **`F1` 轻决策公示块**
4. 未决问题与阻塞点（写明需要用户做什么）
5. 下一阶段进入条件是否已满足（是 / 否 + 依据）

### F3 · 阻塞报告模板（闸门失败或实跑不符时使用）

```markdown
## ⛔ 阻塞：需要你决策

- **现象**：<命令 + 原始报错关键行>
- **根因**：<我定位到的原因，引用 文件路径:行>
- **修法选项**：
  - A. <方案 1>（影响：<文件> / 代价：<描述>）
  - B. <方案 2>（影响：<文件> / 代价：<描述>）
  - C. <方案 3>（影响：<文件> / 代价：<描述>）
- **我的建议**：A / B / C，因为 <一句话理由>
- **在你答复前我不会**：<明确写出我不会做什么>
```

## 7 · skill 使用总则

> 本项目已安装的 skill 清单**只**记录在 `agents/WORKFLOW.md` §5.1（按项目实际安装情况填写），本节不重复罗列。
> **引用、安装、卸载清单之外的任何 skill，一律按重决策处理**（`A3`），须先取得用户同意。

| 编号 | 规定 |
| --- | --- |
| **S1** | skill 是**参考实现与检查清单**，**不是决策来源**。凡 skill 与项目现状冲突，一律进决策点由用户裁定。 |
| **S2** | skill **不得**被用作"不必提问"的理由。 |
| **S3** | 每个 skill 在流程中有**明确的阶段归属与读写边界**（见 `agents/WORKFLOW.md` §5.3）。跨阶段使用需在阶段报告中说明。 |
| **S4** | 安装 / 卸载任何 skill 都属于重决策（`A3`），须先取得用户同意，并说明写入路径是否在项目根目录内。 |
